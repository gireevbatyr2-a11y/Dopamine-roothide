# Что уже есть в открытых источниках

Проверено 2026-11-27. Вопрос был: не тестировал ли кто-то ClearSword/DarkSword на
iOS 15.x и 16.0–16.3.1, чтобы не искать устройства.

Короткий ответ: по **верхней** границе публичные данные совпадают с нашей матрицей,
по **нижней** (15.x, 16.0–16.3.1) публичных прогонов нет — есть только код и
обещания. Наш форк закрывает нижнюю границу иначе, чем апстрим, поэтому чужие
результаты тут не переносятся.

## Уязвимость

**CVE-2025-43520** — состояние гонки в `cluster_write_contig` / `cluster_read_contig`
(DarkSword). По записи CVE:

- затронуты iOS/iPadOS **все версии ниже 18.7.2** и **ниже 26.1**;
- исправлено в **iOS 18.7.2** и **iOS 26.1**;
- «A malicious application may be able to cause unexpected system termination or
  write kernel memory».

Отсюда следует главное: сама уязвимость присутствует на 15.x и 16.x. Открытым
остаётся вопрос не «есть ли баг», а «есть ли у конкретной реализации корректные
офсеты и обход PPL для этой сборки».

- CVE: https://www.cve.org/CVERecord?id=CVE-2025-43520
- Разбор цепочки DarkSword от Google Threat Intelligence:
  https://cloud.google.com/blog/topics/threat-intelligence/darksword-ios-exploit-chain

Записи CVE и разбор Google подтверждают наши верхние границы: 18.7.1 и 26.0.1 —
последние уязвимые версии, 18.7.2 и 26.1 — уже нет.

## Где именно разница с апстримом

`ClearSword/clearsword/utils.c` в апстриме выбирает офсеты по версии так:

```
>= 26.0   ...   socket_so_count = 0x23c
>= 18.0   ...   socket_so_count = 0x254
>= 17.4   ...   socket_so_count = 0x254
>= 17.1   ...   socket_so_count = 0x24c
else      ...   socket_so_count = 0x22c   // TODO: check
                thread_t_ro     = 0x358   // this changes a lot and with different devices
```

То есть для 15.x/16.x/17.0 у апстрима один общий `else` с пометками TODO: значения
не проверены. В нашем дереве эти константы заменены на `koffsetof(...)` из
libjailbreak, который находит структуры патчфайндером XPF в конкретном
kernelcache. Поэтому:

- наш билд не зависит от угаданных констант и в принципе может работать там, где
  апстрим использует TODO-ветку;
- но и чужие «работает/не работает» на 15.x к нам не относятся: у них другие
  значения офсетов.

Для сравнения, значения opa334 (его сборка под 15.x): `so_count = 0x228`,
`icmp6filt = 0x150`. У апстрима ClearSword для 16.x — `0x22c`/`0x150`, у 17.4+ —
`0x254`. Значит офсеты реально расходятся между 15.x и 16.x, и «просто взять
таблицу 16.x» для 15.x нельзя.

## Чего в открытых источниках нет

- Никто не публиковал результаты **персистентности** kernel R/W между запусками
  приложения по версиям iOS. Наш лог с iPhone13,2 / 16.6 (два перезапуска) —
  единственное такое свидетельство, что я нашёл.
- Нет данных по arm64 (A8–A11): и lara, и ClearSword, и opa334 — про arm64e.
  В нашем дереве PPL-обходы есть только для arm64e: `momentarius` (A12/A13,
  15.0–26.0.1), `dmaFail` (A14/A15, 15.0–16.5.1), `Titan` (A14–A17, 16.1–17.3.1).
  Для arm64 PPL-обхода нет ни одного, поэтому A8–A11 выпадают не из-за ClearSword,
  а из-за отсутствия второго примитива.

## Что из этого следует для тестов

Проверять стоит в таком порядке, потому что вероятность успеха падает:

1. **16.0–16.3.1** — офсеты в апстриме есть, PPL-обход (`momentarius` для A12/A13,
   `Titan` для A14–A17) есть.
2. **15.x** — баг есть, офсеты находятся патчфайндером, PPL-обход есть для A12–A15
   (`momentarius` / `dmaFail`), но публичных прогонов ClearSword на 15.x нет.
3. **arm64 (A8–A11)** — PPL-обхода нет в принципе, шансов мало.

Отдельно: `tools/exploit-matrix/matrix.py` считает по plist-ам и поэтому выдаёт
строки вроде «A17 на iOS 15.0» и «A8 поддерживается». Это верхняя оценка модели,
а не реальность: устройств с A17 на 15.0 не существует, а A8 упирается в
отсутствие PPL-обхода. Матрицу читать как «что выберет менеджер эксплойтов», а не
как «на чём заработает».

Диагностика в отчёте тестировщика отвечает на первый вопрос сразу: строка
`xpf: sets struct=1 physrw=1 IOSurface=1 ...` означает, что патчфайндер нашёл всё
необходимое на этой сборке; нули означают, что эксплойт на ней не поедет, и это
видно без паники и без перебора.
