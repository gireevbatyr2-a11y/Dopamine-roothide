# Персистентность kernel R/W между запусками

Задача: после закрытия и открытия приложения kernel R/W должен быть доступен без
повторного запуска эксплойта. Эксплойт нельзя запускать дважды за одну загрузку —
второй прогон ломает состояние ядра и приводит к панике, поэтому «просто запустить
ещё раз» не вариант.

## Почему это вообще работает

У ClearSword примитив R/W — это пара сокетов, у которых испорчен `inpcb`, а
`so_usecount` специально завышен, чтобы ядро не освободило сокет при закрытии fd.
Значит kernel-объекты живут, пока живёт загрузка, и вопрос только в том, как
получить на них новый fd в следующем процессе.

`fileport_makeport` превращает fd в Mach-порт. Порт можно отдать в bootstrap
пространство имён через `bootstrap_register`, и тогда его держит не наш процесс, а
launchd. Следующий запуск делает `bootstrap_look_up` по тому же имени,
`fileport_makefd` — и получает новый fd на тот же сокет. Ядро при этом не
участвует, повторный эксплойт не нужен.

Схема:

```
запуск 1: эксплойт -> сокеты -> fileport_makeport -> bootstrap_register
                                    |
закрытие приложения --------------->| имя и файловый дескриптор остаются у launchd
                                    |
запуск 2: bootstrap_look_up -> fileport_makefd -> kread/kwrite -> готово
```

## Два канала

| Канал | Что делает | Где ожидается |
|---|---|---|
| `simple` | `bootstrap_register` из самого приложения; у приложения есть `com.apple.private.security.no-sandbox`, поэтому и регистрация, и последующий lookup проходят без sandbox-расширений | Проверено на 20G75 (iPhone 12, iOS 16.6), три запуска подряд |
| `launchd` | Если простая регистрация не прошла: `RemoteCall` в launchd выдаёт `sandbox_extension_issue_mach` для register и lookup, примитив регистрируется под именем с UUID-суффиксом | Ожидается на 17+/18/26, где у приложения другой набор прав |

Порядок: сначала `simple`, при неудаче — `launchd`. Записи в `NSUserDefaults`
разные (`KRWPrimitiveSimple` и `KRWPrimitive`), поэтому каналы не мешают друг другу.

## Что проверяется до того, как приложение закроется

1. **Обратный проход fileport** (`persist_probe_fd`): fd → `fileport_makeport` →
   `fileport_makefd` → чтение ядра через новый fd. Если на этой версии порт
   регистрируется, но fd из него не работает, это видно сразу, а не после
   перезапуска, когда примитив уже потерян.
2. **Запись, а не только чтение** (`persist_verify_fds`): читается заголовок Mach-O
   по `kernel_base`, затем в `kernel_base + 4` записывается то же самое значение и
   читается обратно. Примитив только для чтения выглядит здоровым в логе и портит
   первую же запись.
3. **Привязка к загрузке**: в записи лежит `kern.bootsessionuuid`. После
   перезагрузки запись заведомо мертва, её не пытаются искать, а сразу удаляют,
   чтобы приложение ушло в нормальный путь «запустить эксплойт».

## Что делать с неудачей

- Неудачная регистрация второго имени снимает первое: половина застолблённого
  примитива заблокировала бы имя до конца загрузки.
- Неудачная проверка при восстановлении снимает оба имени и удаляет запись.
- Ни один неудачный шаг не оставляет состояние, из-за которого следующий запуск
  будет пытаться восстановить заведомо мёртвый примитив.

## Что показывает отчёт

Строка `persist=` в отчёте тестировщика:

```
record=yes stashed=no recovered=yes channel=simple base=0xfffffff02407c000 boot=same
```

| Поле | Значение |
|---|---|
| `record` | есть ли запись о примитиве |
| `stashed` | застолбил ли этот запуск |
| `recovered` | восстановил ли этот запуск |
| `channel` | `simple` или `launchd` — какой канал сработал |
| `boot` | `same` / `other` — запись из текущей загрузки или из прошлой |
| `failure` | на каком шаге не получилось: `lookup control`, `makefd`, `verify`, `stale boot`, `register rw` и т. п. |

## Как читать отчёты по версиям

| Что в отчёте | Что это значит |
|---|---|
| `stashed=yes` в первом запуске, `recovered=yes channel=simple` во втором | всё работает, канал `simple` |
| `stashed=yes`, второй запуск `recovered=no failure=lookup control` | имя не пережило выход процесса: на этой версии регистрация не передаёт право launchd — нужен канал `launchd` |
| `stashed=no failure=register control` | приложению не дали зарегистрировать имя в этом пространстве имён |
| `stashed=no failure=control fileport round trip` | fileport не даёт рабочий fd на этой сборке — механизм не применим, нужен другой способ держать примитив |
| `recovered=no failure=verify` | fd получен, но чтение/запись не работают: сокет не пережил закрытие, то есть `so_usecount` на этой версии не держит объект |
| `boot=other` | запись от прошлой загрузки, ожидаемо после ребута, приложение должно запустить эксплойт заново |

Первые две строки — то, ради чего нужны тестеры: они показывают, на каких
версиях канал `simple` достаточен, а на каких нужен `launchd`.

## Известные ограничения

- Перезагрузка устройства убивает примитив всегда: сокеты живут в памяти ядра.
  Это не лечится и не должно лечиться.
- Если приложение убито между `fileport_makeport` и `bootstrap_register`, примитив
  теряется, а эксплойт в этой загрузке уже запускать нельзя. Окно — микросекунды,
  но оно есть.
- Канал `launchd` зависит от `RemoteCall`, то есть от корректных офсетов
  `task`/`thread`/`ipc_space`; они берутся из `koffsetof`, поэтому от устройства не
  зависят, но на неизвестной сборке патчфайндер может их не найти — тогда в логе
  будет `xpf: sets ...` с нулями.
